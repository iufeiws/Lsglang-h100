# DSPARK / EP2 退化与速度：静态分析结论 + 下一轮实验（2026-10-25）

本文只基于本目录的日志、各分支源码和 lk_moe 2.7.1 wheel 的反汇编，**没有在 H100 上运行过**。
标"已证实"的结论有日志或代码作证据；标"假设"的需要第 4 节的实验确认。

## 1. 结论速览

| # | 结论 | 状态 |
|---|---|---|
| 1 | #3–#7 的严重退化（工具调用 0/4、复述 8–10/10 错）来自 `9591d76e` 引入的 verify 行布局改动；#8–#10 已不含该问题 | 已证实（矩阵 A/B） |
| 2 | 剩余问题是**低频、偶发的 token 损坏**（贪心 1/20 `DeepSeage`、采样 1–4/20），而不是系统性退化 | 已证实（矩阵） |
| 3 | n=20 分辨不了 0% 和 5%：真实错误率 5% 时，20 次全对的概率是 36%。#9 的 0/20 和 #10 的 1/20 **没有统计差异** | 统计事实 |
| 4 | "DSPARK 本身导致损坏"**尚未被证明**：无 DSPARK 从未在相同 prompt 上跑过 n≥20 | 缺数据 |
| 5 | EP2 下 TP0/TP1（以及 TP2/TP3）的 LK 线程绑在同一批核上（`Process 0/2 ... 48/192 CPUs`，每个核出现两次绑定） | 已证实（日志） |
| 6 | 但把身份改成 `(4, rank)`（fix3）后 pump 瘫痪（用户实测：`link 0.01 GB/s`、`copyiss 25 ms`、prefill 8 tok/s），而 EP1 用同样的 `(4, rank)` + `LK_THREADS=24` 却正常。原因在原生库内部，**fix3 不能用** | 已证实（用户实测） |
| 7 | 只在 EP2 出现的输入：传给 LK 原生库的 `-1` 路由（EP1 每卡持有全部 384 个专家，永远不会出现 `-1`）。fix3 的文档记录过原生"路由计数阶段不跳过负数"；verify 的 6 行会让 `-1` 数量变成 decode 的 6 倍 | 假设 → 实验 C3 |
| 8 | 速度：纯 decode 段 DSPARK 每步约 68 ms（accept ≈ 2.2），无 DSPARK 约 11 ms。池命中率反而更高（97–99% vs 93–97%），GEMM/GEMV 切换对 EP2 速度无影响（31.7 / 30.9 / 31.9）⇒ 瓶颈不在 GPU 池计算 | 已证实（日志） |
| 9 | 光看日志定位不了这 68 ms。需要一份 decode 段的 profile（实验 P1） | 待测 |

已排除的方向（避免重复投入）：

- **跨进程共享内存串扰**：原生库里的 `shm_open` 是静态链接的 cudart 的 IPC 段（`/cudart.shm.*`），不是按 `process_id` 命名的 LK 段。
- **上下文越长越慢**：之前按 6.4k 上下文算出的 175 ms/步是错的。那段时间在跑 recall（`max_tokens=32`），40 步的日志窗口里混进了 prefill。
- **`SGLANG_DSV41_SWA_PAD_SENTINEL=1` / `SGLANG_DSV41_DUMP_FLASHMLA_ARGS=1`**：10 份日志里都没有这两个补丁的生效标记（`[ENV-CHANGE] ... SENTINEL`、`[flashmla-args]`），当前运行态下是空变量。建议从 conf 里删掉，免得以后补丁被重新打上时误触发。
- **fix4 / fix5**（`87192815`、`3eaf4bed`）：只影响启动期 eager 预热的路由。运行期 decode/verify 都在 CUDA graph 里，走不到这段代码。

## 2. 本次代码改动（在 #10 = `d83c3d1a` 基础上）

| 文件 | 改动 | 默认行为是否改变 |
|---|---|---|
| `layer.py` `_fill_remote_routes` + `run_moe_core` | **诊断开关** `LK_EP_FILL_REMOTE_ROUTES=1`：EP>1 时，把交给 LK 的 `-1` 路由换成"本行未使用的本地专家 + 权重 0"，原生库不再看到负数。真实路由与权重逐位不变，MoE 输出数学上不变；代价是权重 0 的路由仍要计算（池 GEMV 和 CPU miss 会多算一些） | 否（默认关） |
| `layer.py` `_init_pool_decode` / `_pool_decode_launch` | 池几何信息补上 `layer` 字段。原代码里 `pool_wait_fence(geo["layer"])` 抛 `KeyError`，又被 `except: pass` 吞掉，导致 `LK_POOL_DET_SPLIT=1` 一直是**静默空操作**（`LK_POOL_SPLIT_PROBE` 同理）。现在失败会告警一次 | 否（这两个开关默认都关） |
| `dspark_verify.py` | 折叠 accept 的结果先 clone 再交出（即 `d06c0d72`）。上游已把读回拷贝排在 forward 后（`scheduler.py:4986`），这里消掉剩下的理论竞争；每步多几个小 kernel | 是（极小开销） |

没有纳入的改动：fix3（见结论 6）；full-rows 契约 `e6a1cef3`（与 #10 质量无可分辨差异）；verify GEMM（EP2 下对速度无影响）；草稿 Q 补零（只影响接受率，不影响输出正确性——贪心输出恒等于 target argmax，拒绝采样也与草稿质量无关）。

`_fill_remote_routes` 的 CPU 单测：2000 组随机 EP2 路由（含整行全 `-1`、候选被占满等边界），验证不再有负数、填入的专家不与本行真实路由重复、真实路由/权重逐位不变、参考 MoE 输出逐位相等。

## 3. 新增脚本（`scripts/`）

| 脚本 | 用途 |
|---|---|
| `recall_margin.py` | 与 `_recall_det.py` 相同的 prompt，贪心跑 N 次，并带 `top_logprobs=5`。对每个与多数输出不同的运行，打印第一个分歧 token 两边的 top-5，并判读："多数运行里该 token 概率 > 5%" 判为近似平局（数值抖动），否则判为"logits 被破坏"。每条结果都落盘为 JSONL |
| `profile_decode_step.py` | 先发一个 1500 token 的长请求，等它进入 decode 后调 `/start_profile` 抓 N 步（CPU+GPU），避开 prefill |

## 4. 下一轮实验（按顺序，每项一次重启）

所有复述类实验都用 `recall_margin.py --n 50`，出现 1 次分歧就能直接做 margin 判读，不必靠计数。

| 实验 | 配置（相对 #10） | 回答的问题 | 判读 |
|---|---|---|---|
| **C1** | 关 DSPARK（#1 配置），本分支代码 | 损坏是否 DSPARK 特有 | 若也出现 `DeepSeage` 类错误 ⇒ 问题在 LK/EP2，DSPARK 是无辜的 |
| **C2** | #10 配置 + 本分支，`LK_EP_FILL_REMOTE_ROUTES=0` | 本分支的对照组 | 应与 #10 同分布 |
| **C3** | 同 C2，`LK_EP_FILL_REMOTE_ROUTES=1` | 原生库对 `-1` 的处理是否导致损坏（结论 7） | n=50 错误显著下降（例如 0/50 对比 C2 的 ≥2/50），并且 margin 判读为"logits 被破坏"的样本消失 ⇒ 坐实 |
| C4 | 同 C2，`--ep-size` 去掉（TP4 EP1；池槽数按 EP1 配，例如 128） | EP2 特有与否 | EP1 干净而 EP2 不干净 ⇒ 结合 C3 定位 |

每轮记下：服务日志、`recall_margin_*.jsonl`、bench JSON。

## 5. 关于 200+ tok/s 的现实评估

- 每步 token 数 = accept len。开放式生成（bench 的 prompt，temp 0.7）实测 accept ≈ 2.0–2.4，recall/工具调用类 3.3–4.4。要在开放式生成上达到 200 tok/s，每步必须 ≤ 11 ms，等于普通 decode 一步的耗时，**在当前架构下不现实**。在 accept ≈ 3.3 的负载上，需要每步 ≤ 16.5 ms。
- EP1 下 GPT 修复版做到了 140 tok/s（accept 2.7 ⇒ 每步约 19 ms），说明 verify 成本是能降下来的；EP2 每步多出来的 50–70 ms 是 EP2+DSPARK 特有的开销，P1 的 profile 之前无法给出修复方案。
- 如果 C1–C4 表明 EP1 无损坏，**最短路径可能是回到 TP4 EP1**：在 EP1 上重新引入 verify GEMM（`9591d76e` 的 `lk_verify.py`，配合 #8/#9 的 full-rows 契约，这个组合在 #8 中质量与基线无差异），并用省下的调试时间提升接受率，而不是继续在 EP2 上排查原生库。
