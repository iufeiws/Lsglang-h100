# DSPARK / EP2：速度与偶发损坏的根因（2026-10-25）

只依据本目录的服务日志、当前代码和 lk_moe 2.7.1 wheel；**不引用 fix3/fix4/fix5 的任何文档**
（它们建立在"fix2 未生效"的错误前提上）。本机无 GPU，结论未经 H100 实跑。

## 1. 速度：verify 的 miss 落在 CPU 关键路径上

纯 decode 段每步耗时（`Decode batch` 每 40 步一行，按 accept/吞吐换算）：

| 运行 | 每步 | 备注 |
|---|---|---|
| 无 DSPARK（#1） | 11.6 ms（p50） | |
| DSPARK #8/#9/#10 bench 段 | 67–69 ms，与 accept、上下文长度无关 | 开放式生成 |
| DSPARK #5/#7 个别窗口 | **16.7 / 17.0 ms**（accept 4.9 / 4.4，约 255–295 tok/s） | 重复型输出，专家全命中 |

池计数（TP0 所在 EP 组，bench 段 dstep 500→600）：命中 +29927、miss +4898，即**每个 verify 步约 49 次
miss 路由，分布在 20 个池层上，平均每层约 2.5 次**。无 DSPARK 时每步约 3 次。

- 6 行 verify 的专家并集比 1 行大 3–4 倍。池覆盖 104/192 个本地专家，命中率在开放式生成下只有 86–96%，
  于是**几乎每层、每步都有 miss 要由 CPU 计算**，而下一层要等这层的 CPU 结果才能开始。
- 全命中时 EP2 + DSPARK 每步约 17 ms，说明 GPU 部分（草稿 + 6 行 verify）本身没问题。
  68 − 17 ≈ 51 ms/步，约等于 20 层 × 每层约 2.5 ms 的 CPU 等待（**估算**）。
- **EP2 的放大因素（日志已证实）**：同一 EP 组的 TP0/TP1 路由完全相同，会同时为同一批专家算 miss；
  而 LK 把两者看成同一个进程（`Process 0/2 ... 48/192 CPUs`），两边的 24 个线程绑在同一组 24 个核上
  （每条 `Backend_NUMA[..] init, thread_id: N cpu_id: M` 都出现两次）。每个进程只能分到一半算力。
  把身份改成 (4, rank)（fix3）会让 pump 瘫痪（用户实测），不可取。

## 2. 偶发 token 损坏：CPU/GPU 拆分没有冻结

每个池层上，GPU 半边（`slot_table_fill` 用 volatile 方式读快照，决定哪些专家由 GPU 计算）和原生 CPU 半边
（决定哪些专家由 CPU 计算）**在不同时刻各自读快照**。如果 pump 在这两次读取之间发布了新槽，同一个专家会被
两边都算一次；如果有槽被换出，就会两边都不算。结果是专家输出被重复累加或漏掉，表现为低频、无规律的错误
token（`DeepSeage`）。verify 的 miss 和 pump 搬运都远多于普通 decode，所以撞上的概率更高；普通 decode 也
同样存在这个窗口，这与"回退到原始版本后仍有退化"相吻合。

lk_moe 自带 `LK_POOL_DET_SPLIT=1` 来解决这个问题：冻结本批次的拆分，GPU 半边等待该批次的拷贝 fence
后再读槽。但原版代码（`main`、#10）里，`pool_wait_fence(geo["layer"], ...)` 因为池几何信息缺少 `layer`
字段而抛出 `KeyError`，又被 `except Exception: pass` 吞掉了：这个开关从来没有真正生效过。

**补上 `layer` 之后实测（2026-10-25 04:40，日志在分支 `diagnose/det-split-capture-failure-20261025`）：
`LK_POOL_DET_SPLIT=1` 与 CUDA graph 不兼容。** fence 在录制期间等待一个录制之外记录的 event，导致录制作废，
target verify graph 在第 3 个 batch size 处崩溃（`cudaErrorStreamCaptureInvalidated`）。decode/verify 都在
graph 中运行，所以这个开关在本部署下不可用；现在录制期间会跳过 fence 并告警，不会再崩溃。**CPU/GPU 拆分竞争
在 graph 下仍未解决**；草稿行的竞争由 `LK_VERIFY_UVA=1` 消除（两半出自同一次读取，见第 5 节），第 0 行的竞争仍在。

## 3. 本分支改动

| 文件 | 改动 |
|---|---|
| `layer.py` | 池几何信息补上 `layer=self.layer_id`；`LK_POOL_DET_SPLIT=1` 在 graph 录制期间跳过 fence 并告警（graph 外仍等待 fence，失败时告警一次） |
| `dspark_verify.py` | 折叠 accept 的结果 clone 后再交出，避免下一次 graph replay 覆盖调度器尚在读取的缓冲区 |

## 4. 部署改动（conf）

```bash
# 不要设置 LK_POOL_DET_SPLIT（与 CUDA graph 不兼容，见第 2 节）
export LK_THREAD_BINDING=NUMA_NODE  # 不改进程身份，消除 TP0/TP1 同核争用（厂商模板的取值）
# 已确认未生效的残留变量，建议删除: SGLANG_DSV41_SWA_PAD_SENTINEL, SGLANG_DSV41_DUMP_FLASHMLA_ARGS
```

启动后检查：日志中应出现 `Using thread binding to NUMA nodes`。`Backend_NUMA ... init` 行在两种绑定方式下
都会打印具体的 cpu_id，无法据此判断线程是否仍挤在同一组核上；需要在运行时检查：
`ps -eLo pid,tid,psr,comm | grep -i python | awk '{print $3}' | sort -n | uniq -c | sort -rn | head`
（如果某些 CPU 上持续有两个计算线程，说明仍在争用）。

验证：`scripts/recall_margin.py --n 50`（贪心复述，带 logprob，结果逐条落盘），以及
`bench_ep2_streams.py --k 1`。

## 5. 草稿行 miss 改由 GPU 经 UVA 计算（`LK_VERIFY_UVA=1`）

不改 lk_moe，也不增加池槽：

- 加载时，池层的 MXFP4 专家 CPU 张量（sglang 自己的 `w13/w2` 及其 E8M0 scale，gate 行在前）在
  `clean_weights_after_loading` 之前保留引用，并用 `cudaHostRegister` 原地 pin 住。
- verify 步的每个池层：
  - **草稿行**（每个请求第 1–5 行）由 GPU 全部算完：常驻专家走原有池 GEMV；未驻留专家由新 kernel
    `sglang.kernels.ops.moe.lk_verify_uva` 经 UVA 直接读取主机权重计算，按专家分组，每个专家的权重只经
    PCIe 读一次，在第二条侧流上与池 kernel 并行。两部分都以同一次 `slot_tab` 读取为准，不存在重复计算或漏算。
  - **第 0 行**（真实 token）照旧交给 lk_moe 原生 `cpu_decode`（草稿行的 id 置 `-1`，按普通 decode
    token 传入）：CPU 每步只算 1 行的 miss，与无 DSPARK decode 相同；pump 的统计和预取以第 0 行为准。
- 激活函数复用 lk_moe 公开的 `_pool_kernel_common._act`，与池 GEMV、CPU 路径的数学一致。

部署：

```bash
export LK_VERIFY_UVA=1        # 需要 LK_VERIFY_RESIDENT=1（当前 conf 已设置）
```

- 主机内存：每卡 pin 约 36 GiB（20 层 × 192 专家），4 卡合计约 144 GiB，是 lk_moe 自身副本之外的额外占用。
- 显存：权重留在主机内存，经 UVA 读取，不占显存；每卡只多约 2.7 MB scratch 和一条 CUDA 流（另有驱动为 pin
  住的主机内存建立的 GPU 页表，量级为几十 MB 以内，未实测）。
  启动时每层打印 `LK_VERIFY_UVA: layer N pinned X GiB of host experts`；如果出现 "draft-row misses stay
  on the CPU" 的告警，说明该层没有启用。
- 关闭只需去掉该变量，代码路径会回到 #10 的行为。

### 复用已有的专家副本（`LK_VERIFY_UVA_PROVIDER`，可选）

不想多 pin 一份时，可以提供现成的专家地址（比如 MoE 后端自己那份）：

```bash
export LK_VERIFY_UVA_PROVIDER="my_pkg.lk_addrs:expert_addresses"
```

```python
# my_pkg/lk_addrs.py
def expert_addresses(*, lk_moe, layer_id, num_experts, hidden, intermediate):
    # 返回 None 表示放弃（该层退回自己 pin 一份副本），
    # 或返回 (w13, s13, w2, s2)：四个长度为 num_experts 的整数地址序列。
    ...
```

契约：
- 每个地址指向该专家的一整块，块内布局与 sglang 的 CPU 参数逐字节相同：
  w13 `[2I, H/2]`（gate 行在前，低 nibble 为偶数位）、s13 `[2I, H/32]` E8M0、w2 `[H, I/2]`、s2 `[H, I/32]`。
  不同专家可以位于任意位置（例如分散在不同的 NUMA 节点上）。
- 地址必须能被 GPU 直接读取：已 `cudaHostRegister` 或 pinned 的主机内存，或者显存。**未注册的主机地址会
  导致 GPU 非法访存，进程直接崩溃**，这一点自检拦不住。
- 启动自检：在 sglang 删除自己的 CPU 副本之前，经 GPU 逐字节比对第 0、E/2、E-1 号专家的四块数据。
  不一致时打印 `addresses from ... do not hold this layer's expert bytes` 并回退到 pin 副本，
  因此布局不对只会多占内存，不会算错。通过时打印 `reads experts at addresses from ...`。

验证：

- 数值：`TRITON_INTERPRET=1 python -m pytest -q test/manual/kernels/test_lk_verify_uva.py`
  （本地 CPU 解释器下 5 项通过，含专家打乱存放和自检拒绝错误地址；在 H100 上去掉
  `TRITON_INTERPRET` 再跑一次 CUDA 版）。gate/up 偏移、草稿行判定、高位 nibble 解码、按专家取地址
  这几处的变异都会使数值用例全部失败。
- 端到端：`bench_ep2_streams.py --k 1`（看每步 ms）、`recall_margin.py --n 50`、工具调用测试。

## 6. GPU 专家缓存：池层的 decode/verify 全部在 GPU 上计算（`LK_GPU_CACHE_SLOTS`）

CPU 只存放权重，不再参与计算；取代 lk_moe 的池（以及第 5 节的 `LK_VERIFY_UVA`）。
开启后，第 20–39 层不再构造 lk_moe 对象，也不再初始化池和 prefill driver：decode/verify（graph）和
prefill 的 late-layer tail（eager）都走同一套 GPU kernel。

- 每个池层（20–39）：S 个显存专家槽 + 全部专家的 pinned 主机副本，外加一张"每个专家一项"的地址表。
  热专家指向显存槽，其余指向主机内存（UVA）。decode/verify 的 graph 里，同一个分组 kernel 一次算完所有行的
  所有路由；每个 tile 只读一次地址表，不存在两边各自决策的问题。
- 换槽：kernel 计算时顺带把每个专家的路由数累加到显存直方图；后台线程每隔一段时间按衰减频次挑出最热的
  未驻留专家，换掉最冷的驻留专家。顺序是：先把换出专家的地址改回主机内存 → 等此前启动的 graph 全部执行完 →
  拷入新专家 → 拷完后再发布新地址。主机和显存的字节完全相同，任何时刻读到哪一边都正确。
- 后台线程的 CUDA 调用都在 `park_lk_moe_expert_pool` 的同一把锁里执行（graph 录制和每次回放启动也持有这把锁），
  并且在第一次 graph 回放之后才开始换槽，此时所有录制和 warmup 都已完成。
- graph 之外的 eager 调用（prefill 中第 20–39 层只算每个请求 tail 的那些行、超出 graph 的 decode batch）
  改由主机规划 tile（按专家排序，每 tile 64 行），每 2048 行一块，临时显存约 0.3 GiB/块，用完即释放；
  eager 所在的 stream 也纳入换槽前的等待，所以换槽不会覆盖 eager kernel 正在读的槽。
- kernel：FP4/e8m0 按位拼成 bf16（与按值相乘的结果完全一致），gate/up 用 bf16 张量核（FP32 累加）；
  down 的激活拆成 bf16 高位 + 低位两次乘（约 16 位尾数），误差远小于 W4A4 原格式本身的量化误差。
  SwiGLU 用 sglang DSv4 的语义（gate 只截上界、up 截两端，同 `expert_pack._clamped_swiglu`），不再依赖 lk_moe。
- `speculative_num_draft_tokens` 在 FusedMoE 初始化时从 `get_spec()` 读取（server_args 里此时还是 None，
  之前 `LK_VERIFY_UVA` 和 `_pool_verify_rows_mult` 因此失效）。

部署：

```bash
export LK_POOL_SLOTS=0          # 关掉 lk_moe 的池，腾出它的显存
export LK_GPU_CACHE_SLOTS=104   # 每层 104 槽 = 18.21 GiB/卡，与原 lk_moe 池（104 槽）相同
# 可选的换槽参数（默认值未经 H100 调优）：
# LK_GPU_CACHE_INTERVAL_MS=200  LK_GPU_CACHE_SWAPS=4（每层每轮最多换几个）
# LK_GPU_CACHE_DECAY=0.8  LK_GPU_CACHE_MIN_GAIN=1.5  LK_GPU_CACHE_LOG_S=30
```

- 显存：只有槽本身（S × 8.97 MiB × 20 层），另加约 17 MB 的 scratch 和输出缓冲。
- 主机内存：每卡 pin 约 36 GiB（sglang 的 CPU 参数本身，原地 pin，不另外复制）；lk_moe 不再构造，它那份副本不再存在。
- eager 临时显存：每块 ≤ 2048 行时 gout_part 240 MiB + mid 54 MiB，块结束即归还给缓存分配器。
- 启动日志：每层打印 `LK_GPU_CACHE_SLOTS: layer N: 104 VRAM slots (... GiB), 192 experts pinned on host (... GiB)`；
  运行中每 30 秒打印 `[gpu-expert-cache] 20 layers, last 30s: routes=... hit=..% swaps=...`。
- 冷启动时槽里先放 0..S-1 号专家，命中率会在开始服务后的几秒内由换槽逐步拉上来。

单层 kernel 基准（不起服务，H100 上直接跑）：
`python debug-snapshot/scripts/bench_gpu_cache_kernel.py --rows 6 12 24 48 --hit 0.9`，
输出每层 ms（×20 即一步里卸载层 MoE 的耗时）、张量核与 FP32 路径的相对误差、eager 路径（prefill tail）每层 ms。

测试：`test/manual/kernels/test_lk_verify_uva.py`（缓存模式：全部路由计算 + 直方图；eager 主机规划：热专家跨多个 tile）、
`test/manual/layers/test_gpu_expert_cache_policy.py`（换槽决策）。本地 CPU 下全部通过；换槽线程与 CUDA graph
的配合只能在 H100 上验证。

## 7. 达到 200+ 还差什么

`NUMA_NODE` 只能消除同核争用（预计 CPU 路径最多快约 2 倍），**不能**把 miss 移出关键路径。
全命中时每步约 17 ms，说明 200–300 tok/s 是可达的；要在开放式生成下也达到这个速度，verify 的 miss 必须
不再阻塞 GPU。可行方向：

1. 原生侧：让 verify 的 miss 直接在 GPU 上计算（GPU 经 UVA 读取主机上的 pinned 权重，每层约 13 MB，
   PCIe 约 0.3 ms，对比现在 CPU 约 2.5 ms），或至少让 CPU 对同一专家的 6 行只读一次权重。
   `pool_layer_info` 没有暴露主机权重地址，Python 侧无法实现，**需要 lk_moe 源码**。
2. 提高池覆盖率（`LK_POOL_SLOTS`，与 KV 容量互相挤占显存）。
