# DSPARK / EP2：速度与偶发损坏的根因（2026-10-25）

只依据本目录的服务日志、当前代码和 lk_moe 2.7.1 wheel；**不引用 fix3/fix4/fix5 的任何文档**
（它们建立在"fix2 未生效"的错误前提上）。本机无 GPU，结论未经 H100 实跑。

## 1. 速度：verify 的 miss 落在 CPU 关键路径上

纯 decode 段每步耗时（`Decode batch` 每 40 步一行，按 accept/吞吐换算）：

| 运行 | 每步 | 备注 |
|---|---|---|
| 无 DSPARK（#1） | 11.6 ms（p50） | |
| DSPARK #8/#9/#10 bench 段 | 67–69 ms，与 accept、上下文长度无关 | 开放式生成 |
| DSPARK #5/#7 个别窗口 | **16.7 / 17.0 ms**（accept 4.9 / 4.4，约 255–295 tok/s） | 重复型输出，专家全命中 |

池计数（TP0 所在 EP 组，bench 段 dstep 500→600）：命中 +29927、miss +4898，即**每个 verify 步约 49 次
miss 路由，分布在 20 个池层上，平均每层约 2.5 次**。无 DSPARK 时每步约 3 次。

- 6 行 verify 的专家并集比 1 行大 3–4 倍。池覆盖 104/192 个本地专家，命中率在开放式生成下只有 86–96%，
  于是**几乎每层、每步都有 miss 要由 CPU 计算**，而下一层要等这层的 CPU 结果才能开始。
- 全命中时 EP2 + DSPARK 每步约 17 ms，说明 GPU 部分（草稿 + 6 行 verify）本身没问题。
  68 − 17 ≈ 51 ms/步，约等于 20 层 × 每层约 2.5 ms 的 CPU 等待（**估算**）。
- **EP2 的放大因素（日志已证实）**：同一 EP 组的 TP0/TP1 路由完全相同，会同时为同一批专家算 miss；
  而 LK 把两者看成同一个进程（`Process 0/2 ... 48/192 CPUs`），两边的 24 个线程绑在同一组 24 个核上
  （每条 `Backend_NUMA[..] init, thread_id: N cpu_id: M` 都出现两次）。每个进程只能分到一半算力。
  把身份改成 (4, rank)（fix3）会让 pump 瘫痪（用户实测），不可取。

## 2. 偶发 token 损坏：CPU/GPU 拆分没有冻结

每个池层上，GPU 半边（`slot_table_fill` 用 volatile 方式读快照，决定哪些专家由 GPU 计算）和原生 CPU 半边
（决定哪些专家由 CPU 计算）**在不同时刻各自读快照**。如果 pump 在这两次读取之间发布了新槽，同一个专家会被
两边都算一次；如果有槽被换出，就会两边都不算。结果是专家输出被重复累加或漏掉，表现为低频、无规律的错误
token（`DeepSeage`）。verify 的 miss 和 pump 搬运都远多于普通 decode，所以撞上的概率更高；普通 decode 也
同样存在这个窗口，这与"回退到原始版本后仍有退化"相吻合。

lk_moe 自带 `LK_POOL_DET_SPLIT=1` 来解决这个问题：冻结本批次的拆分，GPU 半边等待该批次的拷贝 fence
后再读槽。但原版代码（`main`、#10）里，`pool_wait_fence(geo["layer"], ...)` 因为池几何信息缺少 `layer`
字段而抛出 `KeyError`，又被 `except Exception: pass` 吞掉了：**这个开关从来没有真正生效过**（而且开着时
GPU 半边不会等待拷贝 fence，比关着更危险）。

## 3. 本分支改动

| 文件 | 改动 |
|---|---|
| `layer.py` | 池几何信息补上 `layer=self.layer_id`，`LK_POOL_DET_SPLIT=1` 从此真正等待 fence；fence 调用失败时告警一次，不再静默 |
| `dspark_verify.py` | 折叠 accept 的结果 clone 后再交出，避免下一次 graph replay 覆盖调度器尚在读取的缓冲区 |

## 4. 部署改动（conf）

```bash
export LK_POOL_DET_SPLIT=1          # 冻结 CPU/GPU 拆分（需要本分支的 layer.py）
export LK_THREAD_BINDING=NUMA_NODE  # 不改进程身份，消除 TP0/TP1 同核争用（厂商模板的取值）
# 已确认未生效的残留变量，建议删除: SGLANG_DSV41_SWA_PAD_SENTINEL, SGLANG_DSV41_DUMP_FLASHMLA_ARGS
```

启动后检查：日志中不应出现 `LK_POOL_DET_SPLIT: pool_wait_fence failed`（若出现，说明 fence 无法在 CUDA
graph 中录制，需要另行处理）；`Backend_NUMA ... init` 不应再出现同一个 cpu_id 被绑定两次。

验证：`scripts/recall_margin.py --n 50`（贪心复述，带 logprob，结果逐条落盘），以及
`bench_ep2_streams.py --k 1`。

## 5. 草稿行 miss 改由 GPU 经 UVA 计算（`LK_VERIFY_UVA=1`）

不改 lk_moe，也不增加池槽：

- 加载时，池层的 MXFP4 专家 CPU 张量（sglang 自己的 `w13/w2` 及其 E8M0 scale，gate 行在前）在
  `clean_weights_after_loading` 之前保留引用，并用 `cudaHostRegister` 原地 pin 住。
- verify 步的每个池层：
  - **草稿行**（每个请求第 1–5 行）由 GPU 全部算完：常驻专家走原有池 GEMV；未驻留专家由新 kernel
    `sglang.kernels.ops.moe.lk_verify_uva` 经 UVA 直接读取主机权重计算，按专家分组，每个专家的权重只经
    PCIe 读一次，在第二条侧流上与池 kernel 并行。两部分都以同一次 `slot_tab` 读取为准，不存在重复计算或漏算。
  - **第 0 行**（真实 token）照旧交给 lk_moe 原生 `cpu_decode`（草稿行的 id 置 `-1`，按普通 decode
    token 传入）：CPU 每步只算 1 行的 miss，与无 DSPARK decode 相同；pump 的统计和预取以第 0 行为准。
- 激活函数复用 lk_moe 公开的 `_pool_kernel_common._act`，与池 GEMV、CPU 路径的数学一致。

部署：

```bash
export LK_VERIFY_UVA=1        # 需要 LK_VERIFY_RESIDENT=1（当前 conf 已设置）
```

- 主机内存：每卡 pin 约 36 GiB（20 层 × 192 专家），4 卡合计约 144 GiB，是 lk_moe 自身副本之外的额外占用。
- 显存：权重留在主机内存，经 UVA 读取，不占显存；每卡只多约 2.7 MB scratch 和一条 CUDA 流（另有驱动为 pin
  住的主机内存建立的 GPU 页表，量级为几十 MB 以内，未实测）。
  启动时每层打印 `LK_VERIFY_UVA: layer N pinned X GiB of host experts`；如果出现 "draft-row misses stay
  on the CPU" 的告警，说明该层没有启用。
- 关闭只需去掉该变量，代码路径会回到 #10 的行为。

验证：

- 数值：`TRITON_INTERPRET=1 python -m pytest -q test/manual/kernels/test_lk_verify_uva.py`
  （本地 CPU 解释器下 4 项通过；在 H100 上去掉 `TRITON_INTERPRET` 再跑一次 CUDA 版）。三种变异
  （gate/up 偏移、草稿行判定、高位 nibble 解码）均会使全部用例失败。
- 端到端：`bench_ep2_streams.py --k 1`（看每步 ms）、`recall_margin.py --n 50`、工具调用测试。

## 6. 达到 200+ 还差什么

`NUMA_NODE` 只能消除同核争用（预计 CPU 路径最多快约 2 倍），**不能**把 miss 移出关键路径。
全命中时每步约 17 ms，说明 200–300 tok/s 是可达的；要在开放式生成下也达到这个速度，verify 的 miss 必须
不再阻塞 GPU。可行方向：

1. 原生侧：让 verify 的 miss 直接在 GPU 上计算（GPU 经 UVA 读取主机上的 pinned 权重，每层约 13 MB，
   PCIe 约 0.3 ms，对比现在 CPU 约 2.5 ms），或至少让 CPU 对同一专家的 6 行只读一次权重。
   `pool_layer_info` 没有暴露主机权重地址，Python 侧无法实现，**需要 lk_moe 源码**。
2. 提高池覆盖率（`LK_POOL_SLOTS`，与 KV 容量互相挤占显存）。
